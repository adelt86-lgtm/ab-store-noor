# دليل الاستعانة بـ AB Sales ودمج الخدمات في AB Store

**الإصدار:** 1.0  
**التاريخ:** سبتمبر 2026  
**الغرض:** شرح تفصيلي لكيفية الاستفادة من منصة AB Sales (DZ Sales Agent) كمحرك خلفي لـ AB Store Noor دون دمج عشوائي أو تكرار كود.

---

## 1. المبدأ الحاكم

```
AB Store  = الوجه والمنتج البسيط (اكتساب التاجر + متجر + طلبات)
AB Sales  = المحرك الخلفي (واتساب، رد آلي، شحن، تأكيد طلبات)
```

| افعل | لا تفعل |
|------|---------|
| Store يستدعي Sales عبر API داخلي عند الحاجة | نسخ مجلدات Sales داخل مستودع Store |
| التاجر يرى واجهة Store فقط | إجبار التاجر على دخول لوحتين |
| تفعيل القدرات حسب الخطة (Pro / Pro Shipping) | تشغيل كل محرك Sales لكل تاجر Free |
| عزل الأعطال: فشل الشحن لا يوقف المتجر | ربط دورة حياة المتجر بعطل Evolution/Meta |

**جملة واحدة:**  
Store يبيع البساطة. Sales يُشغَّل في الخلفية عند الترقية.

---

## 2. ماذا نأخذ من AB Sales؟ وماذا نترك؟

### 2.1 أولوية عالية — تُدمج مبكراً (مباشرة أو عبر جسر)

| الخدمة في Sales | الاستفادة في Store | المرحلة |
|-----------------|-------------------|---------|
| نموذج الطلبات / العناصر | مرجع لـ `orders` + `order_items` في Store | v1 |
| منطق شركات الشحن (Yalidine, ZR, …) | Pro Shipping: إنشاء طرد + تتبع | v1.5 |
| `shippingService` / `get_shipping_quote` | تسعير ولاية (اختياري لاحقاً) | v1.5–v2 |
| تخزين مفاتيح API للتاجر | حقول مشفّرة على `stores` أو عبر المحرك | v1.5 |

### 2.2 أولوية متوسطة — بعد استقرار الطلبات

| الخدمة | الاستخدام في Store | المرحلة |
|--------|-------------------|---------|
| WhatsApp (Evolution API) | إشعارات طلب جديد للتاجر / رسائل حالة | v1.5–v2 |
| `aiService` + كتالوج | رد آلي على استفسارات الزبائن | v2 |
| تأكيد الطلب من المحادثة | تحديث حالة الطلب في Store | v2 |
| `orderService.syncOrderToExternal` | مزامنة طلب Store → محرك الشحن | v1.5 |

### 2.3 تُترك خارج Store (لا تُعرض كتاجر Store في v1)

| الخدمة | السبب |
|--------|--------|
| Meta OAuth كامل (فيسبوك/إنستغرام) | تعقيد تشغيلي؛ ليس حاجة التاجر الصغير الأولى |
| Telegram كقناة أساسية | واتساب يكفي في الجزائر أولاً |
| Shopify / YouCan / Woo كمصدر كتالوج | Store له كتالوجه الخاص |
| فوترة Paddle/SlickPay المعقدة لـ Sales | Store له مسار ترقية Pro الخاص به |
| واجهات HTML المتعددة لـ Sales | لا تُعرض للتاجر؛ فقط API |

## 3. المعمارية المقترحة

### 3.1 رسم تدفق عالي المستوى

```
[زبون] → متجر AB Store (?store=slug)
              ↓
         طلب جديد (orders + order_items)
              ↓
         لوحة التاجر في Store
              ↓
    ┌─────────┴─────────┐
    │                   │
  Free/Pro         Pro Shipping
    │                   │
 تصدير CSV      API → AB Sales Engine
 نسخ عنوان         إنشاء طرد Yalidine/ZR
                    حفظ tracking_number
```

### 3.2 مكوّنات الدمج

| المكوّن | المكان | الدور |
|---------|--------|--------|
| **Store API** | `ab-store-noor` (Supabase + دوال Edge أو Backend خفيف) | مصدر الحقيقة للطلب والمتجر |
| **Sales Engine API** | `dz-sales-agent` / AB Sales على Railway (أو ما يعادله) | تنفيذ الشحن والواتساب الذكي |
| **جسر داخلي** | خدمة صغيرة أو مسارات في Sales محمية بـ secret | استقبال أوامر من Store فقط |
| **Vault** | Supabase Vault أو تشفير تطبيقي | مفاتيح Yalidine/ZR/Evolution |

### 3.3 قواعد العزل

1. **Store يعمل بدون Sales**  
   إذا المحرك متوقف: المتجر يبيع، الطلب يُحفظ، التاجر يصدّر CSV يدوياً.

2. **Sales لا يكتب فوق كتالوج Store عشوائياً**  
   الكتالوج الأساسي في Store. المحرك يقرأ نسخة/ملخصاً عند الحاجة للرد الآلي لاحقاً.

3. **هوية التاجر**  
   ربط واضح: `store_id` (UUID في Store) ↔ `engine_store_id` أو نفس المعرّف إن وُحّد لاحقاً.

## 4. مراحل الدمج العملية

### المرحلة 0 — قبل أي جسر (أيام v1 الحالية)

**الهدف:** Store مستقل 100٪.

- [ ] تشغيل migrations: `orders` ثم `order_items`
- [ ] لوحة طلبات بالتفاصيل من قاعدة Store فقط
- [ ] تصدير CSV/Excel بصيغة أعمدة Yalidine و ZR (بدون استدعاء API)
- [ ] زر «نسخ عنوان الزبون»
- [ ] QR برابط مطلق + Free/Pro

**لا استدعاء لـ Sales في هذه المرحلة.**

---

### المرحلة 1 — توحيد المفاهيم (بدون شبكة)

**الهدف:** نفس لغة البيانات بين الفريقين/المستودعين.

| المفهوم | في Store | في Sales | قرار التوحيد |
|---------|----------|----------|----------------|
| معرّف المتجر | `stores.id` UUID | غالباً مرتبط بـ stores | خريطة `store_id` ↔ `engine_ref` |
| الطلب | `orders` + `order_items` | orders + بنود | حقول مشتركة للعنوان والهاتف والولاية |
| الحالة | new / confirmed / shipped / done | مشابه | جدول حالات موحّد المعنى |
| الشحن | `shipping_price`, ولاية، منزل/مكتب | شركات + tracking | Store يملك الطلب؛ Sales يملك الطرد |

**مخرجات المرحلة 1:** وثيقة حقول JSON مشتركة لـ «طلب قابل للشحن» (انظر القسم 5).

---

### المرحلة 2 — جسر الشحن (Pro Shipping) — v1.5

**الشرط للبدء:** ≥ 10 تجار على Pro أو طلب واضح من Pilot، وحلقة الطلبات مستقرة.

#### 2.1 ما يُبنى

1. في **Store** (لوحة التاجر):  
   - إعدادات: إدخال `Yalidine API ID/Token` و/أو `ZR Token/Key`  
   - التخزين: مشفّر أو عبر المحرك (لا نص واضح في الجدول)
   - في بطاقة الطلب: زر **«إرسال للشحن»** → اختيار الشركة → تأكيد

2. في **Sales Engine**:  
   - Endpoint داخلي محمي، مثلاً:  
     `POST /internal/v1/shipments`  
   - يستقبل حمولة الطلب + `store_id` + نوع الشركة  
   - يستدعي `yalidineService` أو `zrExpressService` الموجودة  
   - يعيد: `tracking_number`, `label_url` (إن وُجد), `status`

3. في **Store** بعد الرد:  
   - تحديث `orders.tracking_number`, `shipping_company`, `shipping_status`, `shipped_at`  
   - عرض رقم التتبع للتاجر (ولاحقاً للزبون)

#### 2.2 تسلسل الطلب (Sequence)

```
تاجر → [Store Dashboard] زر إرسال للشحن
         → Store Backend يتحقق: plan = pro_shipping؟ مفاتيح موجودة؟
         → POST internal/shipments (Authorization: Bearer ENGINE_SECRET)
         → Sales: create parcel عند الشركة
         → Response { tracking_number, ... }
         → Store: UPDATE orders
         → واجهة: نجاح + رقم التتبع
```

#### 2.3 فشل جزئي

| الحالة | سلوك Store |
|--------|------------|
| المحرك لا يرد | رسالة «تعذّر الشحن الآن — صدّر CSV» |
| مفتاح API خاطئ | رسالة واضحة لإعادة إدخال المفاتيح |
| الشركة رفضت العنوان | عرض رسالة الشركة؛ الطلب يبقى confirmed |

---

### المرحلة 3 — واتساب عبر Evolution — v2 (أو نهاية v1.5)

**الهدف:** إشعار و/أو رد آلي دون أن يبني Store عميل واتساب من الصفر.

#### 3.1 حالات استخدام مرتبة

| # | الاستخدام | من يطلقه | من ينفذه |
|---|-----------|----------|----------|
| 1 | إشعار التاجر: «طلب جديد #123» | Store عند إنشاء الطلب | Sales/Evolution |
| 2 | رسالة للزبون: تم تأكيد الطلب | تاجر من اللوحة أو تلقائي | Sales |
| 3 | رد آلي على استفسار (سعر، توفر) | رسالة واردة للرقم المربوط | `aiService` في Sales |
| 4 | تأكيد طلب من المحادثة يحدّث Store | Sales بعد نية مؤكدة | callback إلى Store |

#### 3.2 الربط التقني المبسّط

1. التاجر من Store: **«تفعيل واتساب الذكي»** (باقة مناسبة).  
2. Store يطلب من المحرك: `POST /internal/v1/whatsapp/provision`  
   - يمرّر `store_id`, اسم المتجر, ملخص كتالوج أو رابط مزامنة.  
3. المحرك يربط جلسة Evolution (QR مرة واحدة أو حسب نظامكم الحالي).  
4. Webhook الوارد عند Sales: إن كان الرد آلياً مفعّلاً → `aiService`.  
5. عند إنشاء طلب من المحادثة:  
   `POST /internal/v1/store-orders` على Store (أو إدراج مشترك متفق عليه) حتى تبقى لوحة Store مصدر العرض للتاجر.

#### 3.3 تحذير Evolution

- الجلسات تنقطع؛ يلزم مراقبة وإعادة QR.  
- لا تعتمدوا الإشعارات الحرجة على واتساب وحده في البداية (اللوحة تبقى المصدر).  
- التزموا بسياسات Meta/WhatsApp عند الانتقال من Evolution إلى API رسمي لاحقاً إن لزم.

---

### المرحلة 4 — مزامنة كتالوج للرد الآلي (v2)

حتى يردّ الـ AI على «عندكم منتج X؟» يحتاج معرفة المنتجات.

**خيارات:**

| الطريقة | الإيجابيات | السلبيات |
|---------|------------|----------|
| أ) دفع الكتالوج عند كل تعديل من Store → Sales | بسيط | تأخير إن نسي الدفع |
| ب) Sales يقرأ من API قراءة فقط على Store | مصدر واحد للحقيقة | يجب تأمين API |
| ج) جدول مشترك في نفس مشروع Supabase | أقل شبكة | يربط قاعدة البيانات بقوة |

**موصى به للبداية:** (ب) أو (أ) دفع عند الحفظ من لوحة المنتجات في Store.

لا تجعلوا Sales يعدّل أسعار Store من المحادثة في v2 الأول.

## 6. الأمن بين المنصتين

| إجراء | التفصيل |
|-------|---------|
| سر مشترك | `ENGINE_INTERNAL_SECRET` قوي؛ يُرسل في header |
| شبكة | إن أمكن: المحرك يقبل الطلبات من IP/خدمة Store فقط |
| لا Service Role في المتصفح | كل الدمج من الخادم إلى الخادم |
| مفاتيح الشحن | Vault / تشفير؛ صلاحية قراءة للتاجر على متجره فقط |
| تسجيل | log لـ `order_id` + نتيجة الشحن بدون تخزين توكنات في السجلات |
| RLS | سياسات Store تمنع تاجراً من شحن طلبات متجر آخر |

## 7. تأثير التسعير على الدمج

| الخطة | ماذا يُفعَّل من المحرك |
|-------|-------------------------|
| **Free** | لا شيء — Store فقط + CSV لاحقاً إن رغتم للجميع أو لـ Pro |
| **Pro** | لا شحن API إلزامي؛ تصدير CSV؛ إزالة الشعار |
| **Pro Shipping** | جسر `shipments` + مفاتيح التاجر + تتبع في اللوحة |
| **لاحق (AI WhatsApp)** | إما ضمن Pro Shipping أو باقة منفصلة «مساعد واتساب» |

لا تفعّلوا Evolution تلقائياً لكل تسجيل مجاني.

---

## 8. خطة تنفيذ مقترحة بالأسابيع

| الأسبوع | العمل | نتيجة ملموسة |
|---------|--------|----------------|
| 1 | إكمال order_items + لوحة التفاصيل في Store فقط | طلب متعدد يظهر صحيحاً |
| 2 | CSV Yalidine/ZR + نسخ عنوان + تثبيت Free/Pro | Pilot بدون محرك |
| 3–4 | Pilot 5–10 تجار؛ قياس: هل يطلبون الشحن؟ | قرار Go/No-Go لـ v1.5 |
| 5–6 | عقد JSON + endpoint `/internal/v1/shipments` + زر في اللوحة | أول طرد حقيقي من لوحة Store |
| 7+ | إشعارات واتساب للتاجر؛ ثم رد آلي محدود | قيمة AI بدون تعقيد الواجهة |

---

## 9. قائمة تحقق قبل استدعاء المحرك من Store

- [ ] الطلب محفوظ في Store مع بنود كاملة  
- [ ] الخطة تسمح بالشحن (`pro_shipping`)  
- [ ] مفاتيح الشركة موجودة وصحيحة  
- [ ] الهاتف والولاية والبلدية ضمن متطلبات الشركة  
- [ ] `ENGINE_INTERNAL_SECRET` مضبوط في البيئتين  
- [ ] timeout واضح (مثلاً 20–30 ثانية) ورسالة فشل مفهومة  
- [ ] لا يُعاد إنشاء طرد لنفس `order_id` مرتين دون قصد (idempotency key)

## 10. أخطاء شائعة يجب تجنبها

1. **دمج المستودعين في monorepo قبل الأوان** — أخّروه حتى يستقر العقد.  
2. **عرض لوحة Sales للتاجر** — يكسّر بساطة Store.  
3. **بناء شحن ثانٍ داخل Store** — تكرار صيانة مع Yalidine/ZR.  
4. **الرد الآلي قبل استقرار الطلب** — رد ذكي على كتالوج فارغ أو قديم يضر السمعة.  
5. **نفس مشروع Supabase بصلاحيات مفتوحة بين النظامين** — بلا حدود خدمة = خطر بيانات.  
6. **بيع Pro Shipping في الإعلانات قبل أول طرد ناجح داخلياً**.

---

## 11. ملخص تنفيذي للإدارة / لنفسك

| سؤال | جواب |
|------|------|
| هل نستعين بـ AB Sales؟ | نعم كمحرك، لا كواجهة بديلة |
| متى الشحن API؟ | بعد v1 وطلبات حقيقية ويفضّل بعد 10 Pro |
| متى واتساب Evolution؟ | بعد الشحن أو معه بحذر؛ الإشعار أولاً ثم الرد الآلي |
| ماذا يبقى في Store دائماً؟ | الكتالوج، السلة، الطلب، اللوحة، Free/Pro، QR |
| ماذا يبقى في Sales؟ | تنفيذ الشحن، جلسات واتساب، AI، تكاملات ثقيلة |

---

## 12. الخطوة التالية المباشرة (بدون كود واسع)

1. إنهاء **order_items** في Store.  
2. كتابة ملف قصير داخلي: **ShipReadyOrder JSON** (القسم 5) ومراجعته مرة واحدة.  
3. عدم فتح جسر الشبكة حتى ينجح Pilot على CSV.
